A filename and byte count describe a result. They don’t prove its contents.
Use surviving metadata to explain how the bytes were assembled, then compare the content hash against a trusted reference.

EVIDENCE INTEGRITY · A TRANSPARENT NOTE

Verify first. If something changes, document it.

All four source images initially matched the published SHA-256 manifest. During analysis, the E02 working copy changed after an HxD save and was quarantined; it was restored from its backup and the restored image matched the manifest. The other three images remained unchanged. This is why the lab emphasizes read-only evidence and repeatable hash checks.

06 WHAT TO TAKE AWAY

Slow down at the point where data becomes a story.

The strongest result is not the most confident one. It is the one whose evidence, reasoning, and limitations are all visible.

Addresses need a base +

Logical partition entries and EBR links use different reference points. Show the base before adding a relative sector count.

Slack is outside the logical file +

Clusters are allocated in units; a file may end before its last cluster does. Raw bytes after EOF are not part of the file’s logical content.

Recovery depends on surviving metadata +

A cleared FAT chain may leave only a start cluster and size. An NTFS run list can preserve extent locations, but neither result should be overstated.

A hash checks bytes—not authorship +

A reference hash can validate content for this test. By itself it cannot identify who made, changed, or deleted a file.

07 QUICK GLOSSARY

LBA

Logical Block Address: a numbered sector on a disk or volume.

Cluster

The file system’s unit of allocation; one or more sectors.

Slack

Allocated bytes after the logical end of a file in its final cluster.

Run list

NTFS metadata describing where a non-resident file’s extents are stored.

Resident data

Small file content stored inside the file’s MFT record.

MD5 / SHA-256

Hash functions used here to compare file content or verify evidence images.
